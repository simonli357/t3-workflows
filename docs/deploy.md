# Deploy a pinned custom T3 release

Use `t3w deploy`; `t3w update` updates the workflow tooling itself. Before installing this patch, the equivalent entrypoint is `node <isolated-source>/deploy/cli.mjs`. Requires Node 22+, Python 3.12, and the existing user service/desktop installation. No tool or skill installation is part of a release deployment.

1. Choose the full source commit and exact custom version. Build with the repository's existing server `build:bundle` / `build:exe` and desktop `dist:desktop:win:x64` (or matching architecture) scripts. Prepare a complete unpacked Linux runtime (`t3`, `client/`, native dependencies/resource monitor), or Windows `server.asar`, `app.asar`, changed existing `server.asar.unpacked/` files and corresponding `client/`. Run isolated packaged-server/client smoke verification. Record source comparison and smoke evidence in `release-spec.json`; a version label alone is not provenance.
2. Put payloads beneath the directory that will contain `release.json`. Adapt `deploy/examples/release-spec.json`, then run `t3w deploy manifest --spec release-spec.json --out release.json`. This inventories every regular file, size, role, SHA-256 and executable mode. Review the manifest once. It pins the commit, server version, platform, client version and any explicit reuse of an older compatible client. Symlinks, traversal, case-colliding names and mixed release identities are rejected.
3. Configure the explicit hosts from `deploy/examples/hosts.json`. Discover the live environment descriptor, installed server hash, served index hash, listener port and actual service/app paths; do not copy yesterday's version or PID. Set disk reserves and a realistic concurrent-growth allowance. The script measures backing filesystems and allocated payload/backup space; Kingston reserves cannot be below 100 GiB, WD below 60 GiB. Stage only on fixed storage. Each host needs the identical reviewed manifest, payload bundle, host config and reviewed scripts at its configured paths. Copy through the existing pinned SSH/file-transfer route **after measuring upload headroom**, then use the CLI to stage into the installation. Transfers and builds are deliberately outside the activation engine; no automatic disk relocation or host configuration is performed.
4. Run `t3w deploy plan --config hosts.json --manifest release.json --target HOST --out plan.json` (repeat `--target` for several). Plan and execution share validators. Read each target's JSON result; exit code 2 indicates blocked/pending/uncertain targets. A pending/offline host is not deployed. `stage` verifies/copies the payload and retains the old installation without stopping it. Running non-Codex sessions, in-flight ownership/moves, ambiguous active states, stale continuation markers, disabled effective continuation settings, mismatched identity/schema or inadequate space block before stop.
5. After release authorization, run `t3w deploy apply --config hosts.json --manifest release.json --target HOST --out apply.json`, then `status` with the same config/manifest/targets and `--out status.json`. `apply` stages first and starts a bounded independent host runner: a separate systemd user unit on Linux, a hidden detached process with an owned Windows job on Windows. Launch failure leaves the old app running. The runner holds the OS lock during activation. Host receipts live in `<T3-base>/runtime/t3w-deploy/<deployment-id>/`; the returned `runnerReceipt` records launch/lock failures separately. Coordinator output retains explicit pending hosts.
6. Retry with `resume` and the **identical manifest and host configuration**. Accepted hosts return their receipt without another activation. An interrupted stage reuses verified files. An uncertain handoff verifies first; it never blindly repeats a stop/update. A Windows replacement interrupted after verified closure can finish the remaining exact old/new resource swaps; a Linux job interrupted after verified closure can invoke the pinned installer. `accepted` means identity, version, client, capabilities, history/ownership/workspace/queue metadata, and native continuation verified. `launched`, `staged`, HTTP ready and PID alive are not acceptance.

To abandon a staged release before any activation, use `t3w deploy cancel --dry-run --config hosts.json --manifest release.json --target HOST`, then the same command without `--dry-run`. The dry run is advisory and does not acquire the host lock. Actual cancellation runs synchronously under that lock and rechecks the exact manifest/config, live old version/environment/install/client, listener ownership, schema, service settings, and all deployment evidence. It budgets only its measured metadata writes; it does not allocate a database backup or migration workspace. Existing provider turns continue normally.

Only a clean `staged` receipt can be cancelled. Any saved activation snapshot/handoff, journal, prepared replacement, apply/resume request, unfinished runner or unknown evidence blocks the operation. Accepted, failed, recovery and uncertain activation states require their existing recovery procedure. Cancellation preserves `receipt.json` byte-for-byte and atomically writes/fsyncs `cancelled.json`, which binds that original receipt and the live observation by hash. CLI `status` reports the effective terminal `cancelled` state. Repeating `cancel` is idempotent, even after a new release claims the host; `apply`, `resume`, `stage` and `plan` for that cancelled id are refused. A different release can claim under the usual OS lock only after validating the terminal cancellation. Preserve both receipt files and all requests.

Adopt the cancellation-aware modules at every entrypoint that can activate the staged release, including frozen deployment copies and installed tooling, before cancelling it. Retain old source/artifacts for audit, not as runnable activation entrypoints. Old wrappers whose module pins no longer match must fail closed; create a separately reviewed wrapper rather than changing the old manifest or host configuration. Obsolete tooling does not understand the new cancellation record.

Cancellation never prunes payloads, runtime trees, previous desktop copies, source bundles or evidence. If another release needs space, use a separately reviewed maintenance inventory after terminal cancellation: identify only that release's inactive staging/runtime tree; require canonical regular files, the exact pinned file/hash/mode set (including the install sentinel), no unknown entries or active references, and a complete reconstructible private archive retained elsewhere. Recheck current host/version and reserves under the host lock before any explicitly released cache removal. Retain receipts, backups, userdata, auth, inboxes and all other releases. No automatic reclamation or database rollback is part of `cancel`.

Linux activation uses the real `t3code.service` user unit, graceful stop, and the staged executable's supported `service install --base-dir ... --allow-downgrade`. This avoids the launcher's trial-update database restore path. Windows identifies the listener's backend and parent executable, gracefully closes those captured processes, swaps verified resources and opens the existing desktop executable. Both reuse the server's shutdown marker and startup reconciliation; the script never sends a conversation prompt. Active Codex sessions must already have effective `continueThreadsAfterServerUpdate=true`. Native provider/account/model/effort bindings must survive and a subsequent native turn must be observed. Other active providers must finish first. User-stopped, snoozed, archived and finished threads are not candidates.

The Linux main unit must match the reviewed protocol-3 archive installer exactly at `~/.config/systemd/user/t3code.service`. Its contents are retained before stop; disk policy must also cover that directory. Existing network/PATH drop-ins can be preserved by setting `serviceDropIns` to the **complete reviewed array of absolute paths and SHA-256 hashes** (see `deploy/examples/myacer-network.json`). Omit the field or use `[]` only for installations without drop-ins. Review bytes before pinning; do not discover and automatically trust new hashes during apply.

This narrow extension accepts canonical `.conf` files in that unit's `.d` directory, containing only `[Service]` and individual quoted `Environment="KEY=value"` assignments for `PATH`, `T3CODE_HOST`, `T3CODE_PORT` and `T3CODE_NO_BROWSER=1`. No duplicate keys, expansion, arbitrary directives, environment files, auth/home overrides or launcher/kill-policy overrides are supported. Paths must have no whitespace. PORT must match the inspected origin. The adapter checks the loaded and on-disk file sets, exact hashes and effective launcher/environment/stop semantics, including daemon-reload state. It rechecks before stop, on closed-phase resume, after backup immediately before install, and during acceptance. The installer replaces only the canonical main unit; these drop-ins are never written or deleted. Their exact bytes/hashes and effective configuration are retained in `previous-service-unit.json`, and the target hash binds the input pins to the deployment receipt. Drift leaves the old host running if detected before stop; after closure it leaves a recoverable closed install for the configuration owner to review before resume.

Completed outgoing moves and cancelled incoming copies may intentionally remain locked. Those terminal records are preserved, not cleared or treated as unfinished transfers. Unresolved move, ownership-transaction and handoff records still block. Preservation fingerprints the real move routes, aliases, authority successor/revision, ownership receipts and native bindings for **all** bound threads. Stopped, finished, snoozed, archived and idle non-Codex threads are checked without starting them. Client acceptance requests and hashes the entire pinned hosted client inventory, including dynamically loaded JS/CSS, fonts and other assets; the same check binds a Windows embedded client to the reviewed client tree.

ProviderService may refresh a stale `runtimePayload.model` during shutdown. When a valid canonical `modelSelection` names the binding's account, verification permits only normalization **to that exact selected model**; selection/options, account, cursor, cwd and runtime mode remain pinned. Missing or unfamiliar selections retain strict comparison. This applies to inactive bindings without starting a turn.

For an existing legacy `recovery-required` receipt, do not edit its baseline. A maintainer may review an explicit `binding-reconciliation.json` sidecar for that deployment. Prepare a private request `{"deployment":"ABSOLUTE_DEPLOYMENT_DIRECTORY","candidates":[{"id":"AFFECTED_THREAD_ID","previousModel":"EXACT_OLD_SHADOW_MODEL"}]}`. The read-only command `python deploy/host.py binding-reconciliation REQUEST.json` emits the proof. Capture its UTF-8 stdout bytes into a new private review file (on Windows use Python subprocess capture, not PowerShell 5 text redirection). It verifies the retained closed backup's checksum/schema/size, reconstructs the **exact original binding hash** by changing only the named redundant shadow, and requires the current binding to match the closed binding. It retains the original failed receipt text and hashes; no cursor or transcript is exported. A wrong guess, material change or absent evidence fails closed.

After reviewing that proof and admitting its measured metadata bytes against existing reserves/growth, retain the exact file exclusively as `<deployment>/binding-reconciliation.json`; never overwrite an existing proof. Validate with `python deploy/host.py binding-reconciliation-check ABSOLUTE_DEPLOYMENT_DIRECTORY`, then use ordinary `resume` with unchanged manifest/config. For verification-only recovery first confirm the recorded activation journal is `started` and the new host is running. The checker revalidates the proof on each verification attempt, the receipt records its SHA-256, and all other preservation/continuation checks still run. Original `before` and closed proofs remain unchanged. Evidence hashing has a 20-second cooperative deadline and the adapter's 30-second subprocess deadline; if it cannot finish, retain recovery-required for review rather than adopting an unmeasured larger budget.

Recovery is bounded: the default runner lifetime is 840 seconds (900-second systemd backstop); a measured backup profile adds only its declared copy/checksum allowances and any configured verification above the original 120 seconds, up to 1,620 seconds (1,680-second systemd backstop), each process/API call has a deadline, and post-start verification defaults to 120 seconds. `recovery-required` retains the prior install, exact phase journal and evidence. Read `receipt.json` and `desktop-activation.json` or `service-activation.json`; use `resume` to verify or finish only the recorded closed phase. If stop occurred before its receipt was saved, an external process reclaimed the port, or installation itself returned an uncertain result, inspect that exact host and finish through its supported installer/start command under the recorded release. Do not delete a claim or change manifest/config to force a retry. A failed continuation remains a failed receipt for human review; do not post mass “continue” prompts.

For **forward migrations**, pin both migration ledgers and schema fingerprints. Read these with `python deploy/host.py database-info ABSOLUTE_DATABASE_PATH` (read-only). Rehearse the exact new packaged server on a consistent isolated copy, using existing isolated-home build/smoke procedures. Retain the before/after fingerprints, preservation/integrity result, covered source-size ceiling and a reviewed upper bound for peak extra migration bytes in `deploy/examples/rehearsal.json` format; hash that evidence into the manifest. Account for table/index copies and WAL, not only final file growth. The planner rejects larger live databases or changed evidence. Both adapters take and verify a consistent **closed** SQLite backup before starting new code. Normal startup applies migrations; acceptance requires the exact new ledger/schema and session/history preservation. The migration-specific recovery procedure is recorded in the manifest.

For databases exceeding the default 270-second helper / 30-second final-checksum window, rehearse the unchanged helper on a closed isolated database at least as large as the declared ceiling. Add `compatibility.database.backup` with `environmentId`, `maxSourceBytes`, `seconds` (270..900), and `rehearsal: {source, sha256}` pointing to its complete fresh `.timing.json`. The helper measures copy, integrity, metadata, fsync and hash separately and supervises their total; a successful fresh run must use at most 75% of the declared allowance. Retained-copy reuse is not a fresh rehearsal.

If the final independent adapter checksum needs more than 30 seconds, also pin `checksumSeconds` (30..120) and `checksumRehearsal: {source, sha256}`. Its JSON must contain `phase: "complete"`, `sourceUnchanged: true`, `budgetSeconds`, `elapsedSeconds`, `bytes` and `sha256`, matching the exact fresh backup proof with at least 25% time headroom. Measure it with `verifyBackupChecksum` from `deploy/native.mjs` against that retained isolated backup; no second large copy is necessary. Retain source lineage and evidence of physical reads so a warmed-cache result is not the only justification. Do not edit an already claimed manifest to introduce a larger budget: prepare a new reviewed input before activation, or explicitly review an existing recovery state.

The adapter checks both size ceilings during plan, after closure and on closed-phase resume. Before stopping it requires enough remaining runner time for stop, the complete helper budget, the complete checksum budget, install/start, configured native verification and receipt margin. It rechecks the remaining allowance before backup and final hash. Exhaustion retains the recorded state; a failed final checksum retains the consistent backup and closed old install. Resume uses a fresh bounded runner, revalidates the original pinned proofs and closed state, independently rehashes the retained backup, and proceeds only if every check passes. A changed checksum, integrity failure or unsupported growth requires inspection, never old-database restoration. On Linux the systemd backstop adds 60 seconds to the guard lifetime; Windows uses the same guard allowance and its owned kill-on-close job.

After a failed migrated start, retain `before-migrations.sqlite` and its checksum receipt. Repair or restart the exact pinned **new** release against the **current** database through its supported service/desktop entrypoint, then use `resume` to verify. Do not start the old code unless a maintainer establishes compatibility with the current schema. Never restore the backup over newer history automatically; inspect it in isolation for recovery. No database restore or previous-install pruning command exists here.

The source-size ceiling is checked again on the actual closed consistent snapshot, including closed-phase resume. That measurement also feeds the disk budget and backup request; the backup transaction rejects a changed size. If shutdown growth exceeds the rehearsal ceiling, backup, replacement and migration startup stop with `recovery-required`. Keep the closed old install and current database. Once its runner has exited, a maintainer may confirm the journal is still `closed`, the ledger/schema are unchanged and no replacement occurred, then start the recorded old service (`systemctl --user start t3code.service`) or existing desktop executable. Retain the claim/receipts for review; a larger rehearsal and explicitly reconciled deployment are required before another migration attempt. Do not raise the bound or rewrite the active manifest to force a retry.

Nonstandard Linux units, new/removal of Windows native dependencies, symlinked package trees, nonlocal/removable storage and unsupported native bindings need a separate reviewed procedure. Desktop updater APIs select their feed's version; this script uses the existing graceful-shutdown continuation hook for pinned custom resources. Interrupted external tool effects cannot be promised exactly once. Concurrent user edits can cause conservative preservation failures; inspect them without discarding history.

Run `node --test --test-concurrency=1 tests/deploy.test.mjs tests/deploy-migration.test.mjs tests/deploy-review.test.mjs tests/deploy-service-config.test.mjs` with `T3W_TEST_PYTHON` pointing to Python 3.12. `T3W_TEST_TMP` selects private fixture storage; service drop-in fixtures require a path without whitespace. Tests use temporary installs, isolated HTTP/SQLite, fake activation commands and a real OS lock; they do not authorize live deployment.

Backup supervision regressions: `python -B tests/deploy-backup.test.py` (Python 3.12, same private `T3W_TEST_TMP`).
